# AIYE 三端同步开发

## 默认范围

- 将 iOS、Android 和微信小程序同时纳入每次功能开发和优化的影响评估与交付范围。
- 本约定替代此前“只更新 Android 和 iOS，暂不更新小程序”的约定。
- 用户提到某端的问题、提供某端截图或引用某端文件，不自动视为只修改该端；检查另外两端是否存在对应功能或同类问题。
- 仅当用户明确要求“只修改某端”或明确排除某端时缩小范围，并在完成说明中注明。
- 平台专属问题可以只改受影响平台，但必须检查其他两端并说明不适用的具体原因，不为凑齐文件改动而修改无关代码。

## 工程定位

| 平台 | 工程目录 | 现有技术栈 |
| --- | --- | --- |
| iOS | `ios_aiye/` | SwiftUI |
| Android | `android_aiye/` | Kotlin、Jetpack Compose |
| 微信小程序 | `wechat_aiye/` | Taro、React、TypeScript、Sass |
| 共享后端 | `backend/` | FastAPI |

以当前源码为准定位页面、组件、数据模型、状态管理和网络请求。保留用户已有改动；注意 iOS 目录可能包含独立 Git 仓库。涉及小程序实现时同时遵循当前可用的小程序专用 Skill。

## 实施流程

1. 阅读三端相关源码及共享接口，列出各端已有能力、差异和本次受影响位置；不得只读截图对应端后直接结束。
2. 确定共同验收标准，覆盖业务规则、字段、导航、权限、加载、空数据、错误状态和关键交互。
3. 同步实现受影响的三端功能。保持业务语义、文案、数据显示、默认值、排序、校验和错误处理一致，复用各端现有组件和设计体系。
4. 界面调整保持三端视觉一致，尤其是按钮尺寸、圆角、描边、间距与信息密度；结合安全区、系统权限和小程序能力作平台适配，不机械复制布局。
5. 接口或数据结构变化时同步检查三端请求参数、响应解析、鉴权、缓存和兼容逻辑；后端修复无需制造客户端改动，但必须检查三端兼容性。
6. 性能优化检查三端同类路径，按各端技术栈分别实现并验证；不要用某端实现直接替代另一端的平台机制。
7. 某端缺少对应功能时，将补齐纳入任务；如需新增权限、付费能力、破坏性数据迁移或明显扩大业务范围，先说明具体取舍并向用户确认。

## 验证与完成标准

- 为受影响端执行可用的构建、静态检查、测试和关键流程验证；根据现有项目脚本选择命令。
- Android 检查相关 Gradle 任务；iOS 检查实际 Xcode 工程与 scheme；小程序检查 `wechat_aiye/package.json`，微信构建使用现有 `build:weapp` 脚本。
- 验证成功、失败、空数据和平台差异场景。界面变更有条件时检查三端实际渲染。
- 不将构建成功等同于设备验证成功；缺少 SDK、模拟器或开发者工具时，明确说明未验证项和阻塞原因。
- 不因某端暂时无法构建而忽略该端实现，不将仅完成一端描述为三端完成。
- 完成说明逐端给出实现和验证状态。无需改动的端写明原因，未完成的端明确列出，不隐去遗漏。
- 将大型构建产物、缓存和测试中间文件放在项目外，遵循项目现有文件管理约定。
